# RFC-001: SDK

## 1. Initialization & Lifecycle

### 1.1 `start(config)` vs `configure() + start()`

These two options provide the same functionality, but the second separates configuration from the lifecycle operation.

#### Decision

Use `configure(config) + start()` instead of `start(config)`.

#### Pros

- Separates configuration from the lifecycle operation.
- `configure()` can be called in a different part of the application than `start()`.
- Makes the API intent clearer.

#### Cons

- Requires the SDK to validate that it has been configured before `start()`.
- Adds an additional API call compared to `start(config)`.

### 1.2 Idempotency

The SDK should prevent incorrect initialization and unexpected runtime behavior when `configure()` or `start()` are called multiple times.

#### Decision

- Calling `start()` before `configure()` throws an error.
- Calling `configure()` multiple times keeps the initial configuration and ignores subsequent configuration attempts. A warning is logged to inform the user.
- Calling `start()` multiple times throws an error.

#### Pros

- Makes incorrect initialization explicit.
- Clearly informs the user about invalid lifecycle calls.
- Prevents accidental reinitialization and duplicate runtime resources.
- Keeps the SDK lifecycle deterministic.

#### Cons

- Adds errors and warnings to the logs for invalid lifecycle calls.
- Requires `configure()` to be called before `start()`.

## 2. Command Routing

### 2.1 Connector Callbacks vs `onCommand()`

#### Option A — Connector Callbacks

The Connector exposes a strict API with a separate callback for each supported command.

Examples:

- `connector.addBreakpoint(listener)`
- `connector.removeBreakpoint(listener)`
- ...

#### Pros

- Clear and explicit Connector interface.
- Strictly defined set of supported commands.
- Command-specific data can be typed at the Connector boundary.

#### Cons

- Changes to the Connector interface can become breaking changes for custom Connectors.
- Adding a new command requires changing the Connector interface.
- The SDK needs additional routing logic to map individual callbacks to command handlers.

#### Option B — `onCommand()`

The Connector exposes a single callback for incoming commands. The SDK receives all commands through this entry point and routes them using its internal command router.

Example:

```ts
connector.onCommand(commandHandler);
```

#### Pros

- Adding new commands does not require changing the Connector interface.
- Single entry point for all incoming commands.
- Keeps command routing inside the SDK.
- Allows flexible routing and handler composition.
- Only SDK knows about supported commands.

#### Cons

- The Connector interface provides less compile-time information about supported commands.
- Command validation and routing become the SDK's responsibility.

#### Decision

Use `onCommand()`.

The Connector should transport commands without depending on SDK-specific concepts such as breakpoints. This keeps the Connector interface stable as the SDK command set evolves.

### 2.2 Unknown commands

Commands with an unknown type must be reported to the console as warnings
without affecting the host application.

#### Options

- **Error + Shutdown** — treat an unknown command as a fatal SDK error.
- **Warning + Ignore** — log a warning and ignore the command.

#### Decision

Use **Warning + Ignore**.

Unknown commands must not affect the host application or terminate the SDK.
The command is logged as a warning and ignored.

Repeated unknown commands should be suppressed to avoid excessive logging.

#### Pros

- Safer for production services.
- Warnings inform the user about unsupported commands.
- Repeated unknown commands do not flood the logs.

#### Cons

- Suppressing repeated warnings may hide a persistent command compatibility issue.
